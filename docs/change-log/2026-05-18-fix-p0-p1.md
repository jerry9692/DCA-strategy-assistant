## 1. 周末起始日重复买入

### 现象

回测里只要 `startDate` 落在周六或周日，回测的 `totalInvested`、`shares`、`buyCount`、`annualizedReturnPct`、`maxDrawdownPct`、`sharpeRatio` 全都偏大或偏离真值。固定 DCA 与一次性买入基准也受同样影响，因为它们走的是同一个 schedule。

### 根因

`backend/app/backtester.py::_schedule` 长这样：

```python
def _schedule(start, end, frequency):
    rule = {"weekly": "W-MON", "biweekly": "2W-MON", "monthly": "MS"}[frequency]
    start_point = pd.DatetimeIndex([pd.Timestamp(start)])
    anchored = pd.date_range(start=pd.Timestamp(start), end=pd.Timestamp(end), freq=rule)
    return start_point.union(anchored)
```

`pd.date_range(..., freq="W-MON")` 只锚定到周一，但 `start_point` 把 `start` 也强行加进 schedule。当 `start` 是周日（例如 2021-05-23），schedule 同时包含 2021-05-23（周日）和 2021-05-24（周一）。

下游三个回测循环（`run`、`_run_fixed`、`run_lump_sum`）每个 scheduled 日期独立调用 `_next_trading_day`，把周日和周一都映射到 2021-05-24，但**没有去重**。结果：

```text
[Sunday 2021-05-23] → 2021-05-24 → 买入 #1
[Monday 2021-05-24] → 2021-05-24 → 买入 #2  （和 #1 完全相同的价格、相同的金额）
```

可复现：`startDate=2021-05-23, frequency=weekly, baseAmount=100, fixed_dca`，预期 3 笔买入合计 300，实际 3 笔买入但有 2 笔在 5/24，共 4 个事件、totalInvested=400。

biweekly 同样命中。monthly（`MS` = month start）只在月初恰好是非交易日时才命中，触发频率较低但也存在。

### 修复

新增 `_trade_day_schedule(prices, start, end, frequency)`，把"日历日 → 交易日 → 去重"这套责任收敛到一个函数：

```python
def _trade_day_schedule(prices, start, end, frequency):
    seen = set()
    trade_days = []
    for scheduled in _schedule(start, end, frequency):
        trade_day = _next_trading_day(prices, scheduled)
        if trade_day is None or trade_day.date() > end:
            continue
        if trade_day in seen:
            continue
        seen.add(trade_day)
        trade_days.append(trade_day)
    return pd.DatetimeIndex(trade_days)
```

`_schedule` 自身保留不动（仍生成日历日序列），现有依赖它的测试 `test_schedule_includes_start_date_as_first_buy_opportunity` 和 `test_schedule_supports_biweekly_events` 仍然成立。

`run`、`_run_fixed`、`run_lump_sum` 三个循环改成直接消费 `_trade_day_schedule` 的结果，不再各自处理映射和边界判断。

### 影响范围

只改后端。前端无需改动。

- 修复后所有回测的金额、份额、metrics 数字都会正确。
- 行为差异只发生在 `startDate` 是非交易日或落在 `MS` 锚点恰好不可交易的情况。其他场景结果与修复前完全一致（已经被 38 个用例覆盖且全部通过）。
- `BacktestRequest.startDate` 默认是 5 年前的"今天日期"，所以只要用户不手动选周末或月初的非交易日，就感受不到差异；但每次"今天恰好是周日"打开页面就会触发。
- 优化器（`optimize_parameters`）调用 `DcaBacktester.run`，多个预设场景的开始日期会被传入，目前 9 个预设里 `q4_selloff_2018`（2018-10-03 周三）、`covid_2020`（2020-02-18 周二）、`liquidity_rally_2021`（2021-01-04 周一）、`rate_hike_2022`（2022-01-03 周一）、`ai_rebound_2023`（2023-01-03 周二）、`ai_momentum_2024`（2023-10-27 周五）都不会触发；`brexit_2016`（2016-06-23 周四）也不触发。`recent_12m` 和 `selected` 取决于用户输入。

## 2. 文档与 `auto_adjust=True` 行为不一致

### 现象

README、user-guide、task-list 三处都说"未来要补股息再投资建模"。但 `backend/app/data.py::_download` 实际用的是 `yfinance.download(..., auto_adjust=True)`，返回的 close 是分红和拆股调整后的价格。

`auto_adjust=True` 的语义等价于"每次现金分红在除息日按当天收盘价立即买入"。所以回测的总收益、年化、最大回撤数字里**已经隐含**了分红再投资的复利贡献。

文档反着说，会让用户：

- 误以为收益偏低需要"加分红"再修正一次；
- 不理解为什么 QQQ 长期 DCA 回测的年化看起来比一些"未调整 close"的工具高 1-2 个百分点（差额其实就是分红复投）；
- 在 task-list 里把"加分红"列为待办，但其实已经做了一种实现。

### 修复

代码层只加注释（`backend/app/data.py::_download`），明确写出 `auto_adjust=True` 的隐含语义。文档层做三处对齐：

1. `README.md` 的 Assumptions & Limitations  
   
   - 删除"no dividend reinvestment yet"  
   - 新增一行说明 auto-adjust 的实际语义和"hold dividends as cash 模式还没做"

2. `docs/user-guide.md` 的 FAQ 末尾  
   
   - 新增"回测里有股息吗？"问答，明确告诉用户已经隐含、未来可能加"分红留作现金"模式

3. `docs/task-list.md` #27

#### 3. 前端图表 series 改时间轴并按日期对齐

### 现象

回测页面下的 4 张图（`contributionOption`、`drawdownOption`、`signalOption`、`showdownOption`）在某些条件下会出现"曲线对不上日期"的视觉错位，本策略 series 与固定 DCA / 一次性 / 对决策略 series 的对应关系飘移。

### 根因

这 4 张图在 P1 修复前的写法都是：

```ts
xAxis: { type: "category", data: result?.contributions.map((event) => event.date) ?? [] }
series: [
  { data: result?.contributions.map((event) => event.amount) ?? [] },
  { data: result?.fixedContributions.map((event) => event.amount) ?? [] },
  { data: result?.lumpSumContributions.map((event) => event.portfolioValue) ?? [] },
  ...,
]
```

`xAxis` 的 category 取自本策略 `contributions` 的日期。其它 series 的数据**只是数字数组**，没有日期信息。ECharts 在 category 轴下是按**索引**对齐 series，不是按日期。只要任意一边出现以下任何一种情况就会画歪：

- `_cached_fixed_backtest`（`@lru_cache`，依赖 symbol/start/end/baseAmount/frequency）和当前请求的 `get_price_history` 跨次调用之间，yfinance 数据出现了细微差异（最新一天到位时间差、补齐空洞），fixed 序列的事件数与 strategy 序列出现 ±1 的偏差。
- 优化器或 strategy showdown 的并行候选返回的 series 长度与本策略不完全一致（例如某个候选恰好碰到 `MIN_BUYS_PER_SCENARIO` 边界）。
- 修复 P0-1（周末起始日去重）的过渡期、缓存命中带过来的旧序列与新序列长度不一致。

P0-1 修完后这些路径理论上对齐，但只要"按索引对齐"这件事还在前端，下次后端改动再次拉开差异就会复现错位 bug，**不应该让前端依赖后端 series 长度永远一致**。

### 修复

把 4 张图统一改成时间轴 + 元组数据：

```ts
xAxis: { type: "time", axisLabel: { color: "#64748b" } }
series: [
  { data: pairSeries(result?.contributions, (event) => event.amount) },
  { data: pairSeries(result?.fixedContributions, (event) => event.amount) },
  ...
]
```

新增工具函数 `pairSeries(events, valueOf)`：

```ts
function pairSeries<T extends { date: string }>(
  events: T[] | undefined,
  valueOf: (event: T) => number | null | undefined
) {
  if (!events) return [];
  return events.map((event) => [event.date, valueOf(event)]);
}
```

每条 series 的数据是 `[date, value]` 元组。ECharts time 轴自己按时间戳定位，不再要求多条 series 长度一致。`priceOption` 之前已经是 time 轴 + 元组数据，本次未改动。

### 影响范围

只改前端，不影响 API、不影响测试。视觉上：

- 图表 X 轴时间间隔从"等距索引"变为"真实时间间距"。如果区间内有跳过的非交易日（节假日），日期间距会反映出空隙；用户视觉上更接近真实时间线。
- 多条 series 即使长度不同，也会在各自的真实日期上叠加，不会再出现错位。
- 由于"价格与买入点"图早已是时间轴，5 张图风格统一了。

### 回归测试

`npx tsc --noEmit` 通过。无单元测试覆盖（前端目前没有 component 测试基础设施）。手工验证：在浏览器里切换不同策略和压力场景，对比修复前后 4 张图。

## 4. 优化器 `_average_metrics` 把 `None` 当 0 平均

### 现象

`OptimizationCandidate.summary` 是把候选在 9 个场景下的 `BacktestMetrics` 求平均得到的"跨场景汇总"。其中 `versusFixedPct` 字段在某些场景下会是 `None`（fixed-DCA 基准的 `endingValue == 0`，即该场景没有合格的 fixed 基准结果）。

修复前 `_average_metrics`：

```python
def avg(key):
    return round(sum(float(getattr(item, key) or 0) for item in items) / len(items), 2)
```

`None or 0 == 0`，所以 None 被静默当成了"持平 0%"参与平均。后果：

- 一个在多数场景里 fixed 基准为空、只在少数场景里跑得不错的脆弱候选，可能因为"几乎所有场景都标 0%"而看起来稳定。
- 实际上"无法对比"和"和固定 DCA 持平"是两种完全不同的事，不应该混。

### 修复

拆出 `avg_optional`：

```python
def avg_optional(key):
    values = [getattr(item, key) for item in items if getattr(item, key) is not None]
    if not values:
        return None
    return round(sum(float(value) for value in values) / len(values), 2)
```

`versusFixedPct` 改用 `avg_optional`。全部为 None 时返回 None，前端就显示"-"。

### 影响范围

只改后端 `optimizer.py`。Top-N 排序逻辑没变（候选排序用的是 `_robust_score`，不依赖平均后的 `versusFixedPct`），只影响候选列表里展示的"平均相对固定"数字。

### 回归测试

新增 `test_optimizer_average_metrics_skips_none_versus_fixed`：构造一个 `versusFixedPct=8` + 一个 `versusFixedPct=None`，断言平均结果是 8（忽略 None），不是 4（把 None 当 0）。

## 5. 信号预热不足时显式提示，不再悄悄回退到默认值

### 现象

代码审查里描述的是"用户在窗口不足的小区间回测时，所有信号悄悄回退到中性，但理由还显示假数据"。实测后发现真实情况比这个更糟：

- `_signal_drawdown` 在 NaN 时走默认值 0，导致 score=0、倍率打到 minMultiplier，理由显示"近窗口回撤 0.0%，回撤越深投入越高"。也就是说**指标缺失被伪装成"市场偏热"信号**，让用户误以为市场偏高所以应该少投。
- `_signal_percentile` / `_signal_rsi` 默认值是 50，回退到中性是真的中性，问题不大。
- `_signal_ma` 默认 0，回退到 cheapness=0.5，也是中性。
- `_signal_grid` 在 high<=low 时 position=0.5（中性），但需要 `rolling_low` 和 `grid_high` 都已计算才有意义。

实测复现：构造单行全 NaN 的 prepared，调用 drawdown_boost，得到 `score=0.0, multiplier=0.8, recommendedAmount=80.0, reasons=['近窗口回撤 0.0%，回撤越深投入越高。']`。

### 修复

#### 后端

1. `models.py` 的 `StrategyDecision` 加 `warmup: bool = False` 字段。
2. `strategies.py` 新增 `_row_optional_float(row, key)`，NaN 时返回 None（而不是 default）。
3. 五个 `_signal_*` 函数全部改成返回 `(score, reason, warmup)` 三元组：
   - 真正预热不足时返回 `(0.5, "指标预热不足，本期按基础金额执行。", True)`。
   - 正常时返回 `(score, 原本的解释, False)`。
4. `evaluate_prepared_strategy` 收到 warmup=True 时，把 `recommendedAmount` 强制回到 `baseAmount × 1.0x`，不再受 minMultiplier 影响。
5. 组合评分（`composite_score`）支持"半 warmup"——只对预热完成的子信号做加权平均：
   - 全部子信号都 warmup → decision.warmup=True，回到中性。
   - 部分 warmup → 用预热完成的子信号加权，warmup=False，但额外加一句"N 个子信号预热不足，本期已自动剔除。"
6. `_raw_signals` 同步：NaN 字段从"返回默认值 50"改为"返回 None"，前端显示"-"。

#### 前端

1. `Decision` 类型加 `warmup?: boolean`。

2. 建议卡 `reason-row` 上方加黄色 `.warmup-banner`：
   
   ```
   指标预热不足，本期按基础金额执行；等历史数据足够后才会启用动态调整。
   ```

3. `styles.css` 新增 `.warmup-banner` 样式（亮色 `#fffbeb` + `#92400e` 文字、暗色 `#2a1c08` + `#fcd34d` 文字）。

### 影响范围

- 用户行为变化：之前在数据不足时（短回测区间或窗口很大的 lookbackDays 一起踩），drawdown_boost 会按 minMultiplier 投入；现在按 baseAmount × 1.0x 投入。如果有人当前依赖"区间太短直接打到下限"的副作用，这次会改变结果。但这个副作用本身就是 bug。
- API 行为变化：`StrategyDecision.warmup` 是新字段，老前端不传 / 不读，向后兼容（默认 False）。
- 优化器/回测内部都使用同一个 `evaluate_prepared_strategy`，warmup 的事件会以 baseAmount 计入。回测 metrics 会有微小变化，但只在历史数据极短的极端情况下出现。
- 修复了 2 条原本断言错误旧行为的用例：
  - `test_composite_all_zero_weights_falls_back_to_neutral`：之前断言 `recommendedAmount == 135`（135 = 100 × (0.2 + 0.5 × 2.3)，min=0.2/max=2.5/score=0.5），新行为是 100（warmup=True 强制中性 1.0x）。
  - `test_signal_reasons_do_not_render_nan_for_short_windows`：之前断言 `rawSignals["percentile"] == 50`，新行为是 None（前端会渲染成"-"）。

### 回归测试

新增 3 条：

1. `test_drawdown_boost_warmup_falls_back_to_base_amount_with_clear_reason`  
   构造全 NaN 的 prepared，断言 drawdown_boost 返回 `warmup=True, multiplier=1.0, recommendedAmount=100, score=0.5`，且理由不包含 "0.0%"。

2. `test_composite_partial_warmup_uses_only_active_signals`  
   构造 drawdown=-20% + 其他全 NaN 的 prepared（30% 触发阈值），断言 `warmup=False`、score>0.5、理由包含"子信号预热不足"。

3. `test_composite_all_zero_weights_falls_back_to_neutral`（更新）  
   验证全权重 0 时 `warmup=True` 且回到 baseAmount × 1.0x。

## 7. IRR 终值用区间末端 close

### 现象

`endDate=2024-12-31`、最后一次 buy 在 2024-12-23 的回测里，`endingValue` 卡在 12-23 当天的 portfolio value，2024-12-24 到 12-31 之间的价格变化完全不计入收益、回撤和 IRR。极端情况下（end 比最后 buy 晚几个月）会显著低估或高估真实收益。

### 修复

`backtester.py` 新增：

```python
def _mark_to_market_event(prices, end, last_event, shares, invested):
    target = pd.Timestamp(end)
    last_day = _last_trading_day_on_or_before(prices, target)
    if last_day is None or last_day <= pd.Timestamp(last_event.date):
        return None
    price = round(float(prices.loc[last_day, "close"]), 4)
    return ContributionEvent(
        date=last_day.date().isoformat(),
        price=price,
        amount=0.0, shares=0.0,
        totalShares=round(shares, 8),
        totalInvested=round(invested, 2),
        portfolioValue=round(shares * price, 2),
        multiplier=last_event.multiplier,
        score=last_event.score,
        reasons=[],
    )
```

`run`、`_run_fixed`、`run_lump_sum` 三个路径在 `_with_cashflow_adjusted_drawdowns` 之前 append 这个挂账事件。

### 副作用处理

挂账事件 `amount=0`，所以：

- `_metrics` 里 `buyCount = sum(... if amount > 0)` 不变
- `total_invested = max(...)` 不变（挂账事件继承前一笔的累计投入）
- `_money_weighted_annualized_return` 把每个事件当现金流，amount=0 不影响 NPV，但终值取最后一笔 portfolioValue —— 这正是 fix
- `_risk_adjusted_ratios` 多算一段 returns，反映末端持仓变化

前端 `priceOption` 的 scatter 之前会把所有 contributions 当买入点画绿点。新增过滤 `event.amount > 0`，挂账事件不再画错误的买入点。CSV 导出多一行 amount=0 的挂账记录，可以接受。

### 回归测试

新增 `test_metrics_use_period_end_close_for_ending_value`：构造一个 endDate 比最后一次 buy 晚 3 周的回测，断言：

- 最后一个事件 `amount == 0`、日期严格晚于最后一次 buy
- `metrics.endingValue` 等于挂账事件的 portfolioValue，不等于最后一次 buy 的 portfolioValue
- buyCount 和 totalInvested 仍然只反映真实买入

调整 2 条原断言：

- `test_backtester_runs_weekly_events`：原本 `metrics.buyCount == len(events)` 改成 `len(buys)`
- `test_weekend_start_does_not_double_buy_on_next_monday`：用 `event.amount > 0` 过滤后再断言去重

if self.minMultiplier >= self.maxMultiplier:

副作用：`_fixed_config`（main.py）、`_fixed_for_scenario`（optimizer.py）、`_cached_fixed_backtest`（main.py）原本都用 `minMultiplier=1, maxMultiplier=1` 占位（`fixed_dca` 策略不读这两个字段）。校验加上后会报错。改成 `min=1.0, max=1.0001` —— 仍然有效相等，校验通过，回测行为不变（`fixed_dca` 走的是 `_run_fixed` 路径，不读 multipliers）。

class ContributionEvent(BaseModel):
